# 钢四人物小传MOD · 维护流程

> 定位：本仓库唯一流程文档。根 `AGENTS.md` 管项目定位、任务路由、安全红线与权威文档指针；本文管三类任务通道的执行口径与验证分层。发布闸门见 `docs/RELEASE_CHECKLIST.md`，工坊上传见 `docs/WORKSHOP_UPLOAD.md`。

## 一、三类任务通道

### 1. 普通讨论与只读检查

直接处理：不建卡、不落盘、不跑审计。只读扫描、问答、排查分析都属于这一类。

### 2. 小型、可逆、范围清楚的变更

流程：明确改动范围（改什么/为什么/不改什么）→ 只读扫描 → 改 → 针对性验证 → 展示 diff → 机主明确确认 → 提交。

- 不建任务卡、不强制独立模型复验——由当前 Agent 完成并验证即可。只有机主对结果不满意、任务存在疑点，或命中高风险条件时，才调用 Codex 或其他独立模型复验。
- 验证按实际风险选择，不默认全量审计：
  - 纯文档改动：`git diff --check`＋相关链接/指针检查＋针对性检查。只改 `AGENTS.md` 时加跑 `python tools/check_snapshot.py`（它校验入口指针），不强制完整 audit。
  - `src/` 内容改动：`python tools/audit_all.py` 全绿。
  - 检查器改动（`tools/check_*.py`、`common.py`、`self_test.py`）：先 `python tools/self_test.py`，再跑相关审计。

### 3. 高风险变更

命中任一条件即高风险：修改 `src/full_only/`；游戏逻辑或身份语义（ideology/traits/角色ID/上台逻辑等）；史实来源存疑；批量正文；双版本结构（shared/full_only 拆分、packaging）；修改 `docs/CURRENT_BASELINE.md`、`docs/HUMAN_DECISIONS.md` 及其 JSON 台账；稳定版转正；发布与工坊上传。

流程：

1. **需求门**：与机主确认做什么/边界/不做什么；机主明确同意才进方案。
2. **方案门**：改动点、风险、回退、验收标准落清；机主明确同意才动手。
3. **开工前检查**：记录当前 HEAD 与 `git status`，确认任务涉及路径没有未处理改动；不得为了制造干净基线而自动提交用户改动；既有改动与任务重叠时，停止并报告。
4. **小步实现**：每步跑 `python tools/audit_all.py`（`full_only` 变化含原版语义比对）。
5. **提交前独立复验**：由当时可用的独立模型（K3、Codex 或其他合适模型）审方案/diff，输出「通过/需修改＋问题位置＋修改思路」，修到通过。**必须在提交前完成，不得先提交后补检**。执行者在使用时检测可用性；仓库不记录固定模型版本、provider、端点；密钥永不入库、永不进文档。
6. **机主明确确认后提交**。提交、合并、标签与发布均须机主明确授权；推送涉及外部写入，必须机主明确说出「推送」。

任务卡仅在需要跨对话、跨多步骤推进或确有复杂决策需要持久交接时使用（见 `docs/scaffold/任务卡机制说明.md`）；即使不建卡，上述需求门、方案门、验证与提交前独立复验仍必须执行。

### 单篇小传与别名特别条款

已核实来源且经机主逐字批准的单篇小传或别名维护，按小型变更通道处理，不因「正文入包」四字自动升级为高风险；人工批准与 `audit_all.py` 内容审计不省。

## 二、实机证据分层

- 画面显示类问题以机主点验或截图为主要证据；错误诊断才需要日志判读（`tools/check_logs_cbio.py`）。`result.json` 只证明日志判读结论，不能替代游戏画面或功能证据。
- 日常点验：按当次断言需要保存证据，不固定格式、不强制归档。
- 发布、稳定版转正和高风险回归：执行完整归档（`docs/testing/实机回归归档制度_钢四裁剪版.md`）；回归从黄金存档出发（`docs/testing/黄金存档制度_钢四裁剪版.md`）。

## 三、纪律

1. 推送必须机主明确授权（明确说出「推送」）；不得从「确认」「照批」「按推荐」推断提交或推送授权。
2. AI 不得自封「稳定版」；只有机主实机确认后才允许更新 `docs/CURRENT_BASELINE.md`、合并 `main`、打 `*-stable` 标签。
3. 密钥红线：模型 API key、Steam 密码/Guard 验证码等机密永不入库、永不进文档。
4. 发布/构建/上传使用现成工具与清单（`tools/build_release.py`、`docs/RELEASE_CHECKLIST.md`、`docs/WORKSHOP_UPLOAD.md`），不得绕开自造轮子；AI 不得自行上传工坊。

## 附录：命令速查（按需参考，非自动流程）

> 以下摘自历史维护实践，按需取用。普通个人维护不强制开分支；任何提交、合并、标签和发布仍须符合机主授权。

- 任务分支（可选）：`git switch main` → `git status --short` → `git switch -c fix/任务英文短名`。
- 只读扫描输出格式：确认事实、推测、问题证据、涉及文件、最小修复方案、允许 diff、需要的原版比对和游戏测试。机器底库候选不得直接视为确认 BUG。
- 日常审计：`python tools/audit_all.py`；改动检查器后先 `python tools/self_test.py`（金丝雀）。
- 构建（发布准备时；输出在 `releases/`，不提交 Git）：`python tools/build_release.py --version <下一版本>-test`。
- 部署实测：构建结果复制到游戏用户目录 `mod\`（本机路径运行时确认）；开发期目录名加 `_dev` 后缀与正式版区分，转正后删除 dev 目录。
- 日志：游戏用户目录 `logs\`（本机路径运行时确认），AI 直读判读，不需机主转发；日志解释与原版噪声归因见 `docs/ENGINEERING_PLAYBOOK.md` 第 10 节。
- 稳定化（仅机主实机确认并明确授权后）：合并任务分支（`git merge --no-ff`）、打 `*-stable` 标签、更新 `docs/CURRENT_BASELINE.md` 与 `CHANGELOG.md`。
