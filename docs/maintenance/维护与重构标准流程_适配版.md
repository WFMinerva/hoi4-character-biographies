# 钢四人物小传MOD · 维护与重构标准流程（适配版）

> 状态：2026-08-20 门二已拍板（全量落地）并落地本仓库，即日生效。本流程自身的后续修改同样走本流程（三扇门）。
> 定位：动手之前的强制流程。由《开局一键爽玩》`docs/maintenance/维护与重构标准流程.md` 按本 MOD 规模裁剪适配：本流程管动手前，根 `AGENTS.md` 红线管改动之中，`tools/audit_all.py` 与 `docs/RELEASE_CHECKLIST.md` 管改动后；发布（构建/工坊/Git 标签）仍按既有发布门禁，不在本流程内。
> 适用范围：一律强制——维护、重构、新功能、文档改动（含本流程文档本身）。

## 一、三级流程（先判级，三问定档，拿不准从高不从低）

1. 是已有功能维护，还是新功能/跨模块大重构？新功能（新显示机制攻关、新小传批次线）或大重构（`full_only` 覆盖全量重建、双版拆分模型变更）→ **A**。
2. 改动多大？局部几行改 bug/文案/单条正文/单个 desc 别名 → **B**；加功能/批量正文整合/覆盖文件重建/工具与依赖变更 → **C**。
3. 影响面？C 中动 `src/full_only/` 原版覆盖、身份语义（ideology/traits/角色ID/上台逻辑）、七国历史文件、双版拆分，或预计超过约 200 行 / 5 个文件 → **门二必须等机主拍板**。

### A. 立项全流程（六步）

| 步 | 内容 | 门 |
|---|---|---|
| ① 对齐需求 | 与机主确认做什么/边界/不做什么；问答原文与结论记入方案文档「需求」节 | 门一：机主拍板才进② |
| ② 调研 | 原版文件（`reference/` 指向 HOI4 1.19.2）、`docs/` 各手册（ENGINEERING/TEXT/INCIDENTS/KNOWN_RISKS）、工坊同类 MOD；本机可实测的并行实测 | 自主推进 |
| ③ 再次对齐 | 带调研结论回机主核对方向；方向变更需机主认可 | 自主推进 |
| ④ 分步方案 | 方案文档落盘：需求、调研、分步改动点、风险、回滚、验收标准 | 门二：机主拍板才进⑤ |
| ⑤ K3 复检 | 把方案文档与验收标准交 K3 独立审计（执行口径见第三节），输出「通过/需修改+问题位置+修改思路」，修到通过 | 方案复检通过才进⑥ |
| ⑥ 经确认提交 | 小步实现（每步过 `audit_all.py` 门禁）→ 改动 diff 经 K3 复检通过 → 机主确认 → git commit（`fix/` 分支 + `merge --no-ff` 回 main，或按任务裁定） | 门三：机主确认才提交；推送仅凭「推送」二字 |

### B. 轻流程（小修/改 bug/文案/单条正文）

对齐改什么（一句话说清）→ 改 → `python tools/audit_all.py` 全绿 → K3 复检（审 diff）→ 机主确认提交。变更记录追加到《开发状态快照与交接》「变更记录」节，不另起炉灶。

### C. 维护升级流程（加功能、重构、覆盖重建）

| 步 | 内容 | 门 |
|---|---|---|
| ① 对齐改什么 | 报改动范围+为什么+不改什么；记入变更记录草稿 | 门一：机主拍板 |
| ② 立基线 | git 提交干净基线；跑 `python tools/audit_all.py` 留底（不含构建） | 自主推进 |
| ③ 轻调研 | 只在进新领域才调研（新引擎命令/新机制/新 DLC），否则跳过 | 自主推进 |
| ④ 分步方案 | 快照文档追加「变更记录 #n」：日期/需求/方案/验收/回滚 | 门二按阈值：动 full_only/身份语义/七国文件或改动大才等机主拍板 |
| ⑤ 小步实现+每步回归 | 每步改完先跑 `audit_all.py`（旧功能不破，full_only 变化含原版语义比对）再验新功能 | 自主推进 |
| ⑥ K3 复检 | 审本次 diff，修到通过，逐轮记录 | 通过才进⑦ |
| ⑦ 经确认提交 | 机主确认 → git commit；同步更新受影响文档 | 门三；推送仅凭「推送」二字 |

## 二、三扇门（必须等机主拍板，其余自主推进）

1. 需求对齐（A①/C① 结束）；2. 方案拍板（A④ 必设，C④ 按阈值）；3. 提交确认（A⑥/C⑦/B 结束）。
另：推送仅凭「推送」二字；构建/发布/工坊上传按 `docs/RELEASE_CHECKLIST.md` 与 `docs/WORKSHOP_UPLOAD.md` 执行，不因本流程缩短；**工坊上传由机主本人执行 steamcmd（AI 只做到登录前）**。
固定约定（2026-08-20 机主指定）：每次到门，AI 报告同步给 2–4 个建议选项——推荐第一标「（推荐）」，每项一句取舍；机主点选或回「选 n」/「按推荐」即拍板生效，自由回复不锁死；弹窗不可用降级正文编号列表；**推送永不进选项**（仅凭「推送」二字）。

## 三、K3 复检执行口径

- 执行：本机 kimi CLI（0.36.1，2026-08-20 冒烟通过），命令 `kimi -m moonshot/k3 -p 审计提示词`；专用 API key 由机主提供、只存本机 kimi CLI 配置，**永不入库、永不进文档**。
- 给审计看：本次方案/改动 diff、验收标准与相关红线；要求输出「通过 / 需修改 + 问题位置 + 修改思路」，片段 ≤5 行，禁止泛泛而谈，不输出完整代码。
- 需修改的落实后必须再次复检，修到通过为止；每轮结论与修复落点记录在案。
- 通道背景（留档）：爽玩项目实测 kimi CLI + moonshot/k3 可用（2026-08-18 固化）；本机 2026-08-20 冒烟测试回复「通道OK」。日后通道变化以当时可用者为准，不跳步。

## 四、与既有门禁的衔接

本流程（动手前）→ 根 `AGENTS.md` 修改红线与 `src/shared/AGENTS.md`、`src/full_only/AGENTS.md`（改动之中）→ 审计与验证（改动之后）→ 实机回归（最小集监测，见第五节）→ 文档 → 构建与 SHA → 机主确认 → 标签/工坊。

内容改动后必须依次执行：

```powershell
python tools/audit_all.py
```

改动 `tools/` 下任何检查器后，先跑金丝雀：

```powershell
python tools/self_test.py
```

构建（发布准备时；构建输出在 `releases/`，不提交 Git）：

```powershell
python tools/build_release.py --version <下一版本>-test
```

每步回归强度分级：A 流程每步过完整审计（`audit_all.py`，full_only 变化时含 `compare_with_vanilla.py` 原版语义比对）；C 流程每步只跑 `audit_all.py`（不含构建），构建留到发布准备。

发布/构建/上传纪律：动手前先列出 `tools/` 并读 `docs/RELEASE_CHECKLIST.md`、`docs/WORKSHOP_UPLOAD.md`，确认既有脚本与方法再执行；不得绕开现成工具自造轮子；AI 不得自行上传工坊。

## 五、实机监测最小集（2026-08 起，按本 MOD 裁剪）

本 MOD 无 `OCS_TEST` 自检机制，最小集从以下三项起步（爽玩全套裁剪而来）：

1. **黄金存档**：1936/1939 各一份；登记六项（用途、游戏版本 `code_revisions.log`、MOD 版本线、创建日期、SHA-256、本机位置）；哈希入仓、二进制不入 git；实测后另存判定档，不覆盖黄金档。制度见 `docs/testing/黄金存档制度_钢四裁剪版.md`。
2. **日志判读**：裁剪版 `tools/check_logs_cbio.py`——`error.log` 全行白名单、`game.log` 仅「错误样」行、`text.log` 非 0 字节告警、`setup.log` 存在性＋加载摘要；本 MOD 无标记机制，不适用标记铁律（工具内注明）。白名单 `tools/cbio_log_whitelist.json` 从本机历史日志逐步建。
3. **回归归档**：`docs/testing/<版本-轮次>/` 裁剪四件套（`README.md`/`清单.md`/日志脱敏副本/按需截图，result 存 `audit/reports/`）；逐项必填、缺证据＝`FAIL_NOT_EVIDENCED`。制度见 `docs/testing/实机回归归档制度_钢四裁剪版.md`。

判读口径沿用 `docs/ENGINEERING_PLAYBOOK.md` 第 10 节与 `docs/INCIDENTS_AND_SOLUTIONS.md`；实机点验本身由机主执行，AI 负责判读、脱敏、归档与报告。

## 六、纪律

1. 一律强制：维护、重构、功能、文档改动均走本流程；未经确认不动手、不提交。
2. 全程留痕：对齐问答、调研出处、方案、验证记录、K3 逐轮历程全部落盘。
3. 密钥红线：kimi 专用 key、Steam 密码/Guard 验证码等机密永不入库、永不进文档。
4. 基线先行（C 流程）：动手前先 git 提交干净基线；每步回归旧功能——维护最大的风险是修坏旧功能（尤其 full_only 覆盖回退原版逻辑，见 INCIDENTS 第 1 条）。
5. 提交信息中文摘要式短句；提交与推送分离，推送仅凭「推送」二字；只有机主实机确认后才允许更新 `docs/CURRENT_BASELINE.md`、打 `*-stable` 标签。
