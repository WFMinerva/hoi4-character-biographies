## 1. 强制工作流程：先确认，再处理

### 1.1 文件点名确认

用户上传文件后，第一步必须做“文件点名确认”，不得直接整合、查错或打包。

点名确认至少包括：

- 看到了哪些文件。
- 哪个是当前基准包。
- 哪个是待处理文件。
- 哪个只是参考资料。
- 哪个是日志、截图、表格、游戏本体资料或旧版本包。
- 当前是否还缺文件。
- 当前任务是否需要用户进一步确认。

不得凭文件名、历史记忆或旧项目规范自动认定当前基准。用户明确说“这是当前最新基准包”的文件，才是当前基准。

### 1.2 基准确认

如果出现多个 MOD 包，必须确认版本线：

- 当前基础包是哪一个。
- 旧包是否只是对照或参考。
- 是否需要对比两个版本。
- 是否需要从旧包提取某项修复。
- 是否禁止恢复旧功能线。

如果用户没有明确指定，不得自行选择版本线。

### 1.3 任务分流

确认基准后，再判断任务类型：

- 整合文本：读取人工复核表或文本表，确认哪些是已审核、待审核、待替换、待新增。
- 查日志：必须结合当前 MOD 包本体，不只看日志。
- 打包 MOD：先自检路径、文件夹名、`.mod`、`descriptor.mod`、无关文件、编码和日志风险。
- 做对比表：明确比较对象、比较字段、是否以用户人工修改版为准。
- 提取润色表：只提取可审稿文本，不把技术字段混入 Claude 写作任务。
- 补漏显人物：先查显示路径，不直接判定缺文本。

### 1.4 状态分级

任何 bug 或修复状态必须分级表达：

- 截图确认：用户截图或助手截图能直接看到现象。
- 日志确认：日志中有明确报错、缺本地化、重复 key、语法错误等证据。
- 试玩确认：用户实际进游戏测试确认。
- 人工确认：用户明确说文本或修复已人工审核/确认。
- 文件确认：助手检查文件结构或文本存在，但未进游戏测试。
- 阶段性可接受：目前没有发现明显问题，但不能写成彻底修复。

“看着没问题”“暂时可以”“初查无明显问题”只能标为阶段性可接受，不能标为彻底修复。

### 1.5 更新 source 的规则

本文件只有在长期流程、长期技术规范、长期文本标准发生变化时才需要更新。

不得因为某一轮版本更新，就把当前版本号、当前包名、当前表名、当前待修复人物名单写进本 source。版本更新时，只更新当前交接卡、更新日志或版本说明；除非流程规则本身改变，否则不改本文件。

## 2. 判断标签与置信度规则

### 2.1 判断标签

后续分析、判断和问题定位时，尽量给关键判断打标签：

- `[KNOWN]`：训练事实、文件明示内容、用户明确说明、日志明确显示。
- `[COMPUTED]`：脚本扫描、计数、对比、校验得出的结果。
- `[INFERRED]`：根据文件结构、脚本关系或现象推论。
- `[COMMON]`：通用领域知识。
- `[FRAME]`：符号体系、工作框架、内部分类，不等于现实事实。
- `[GUESS]`：缺少根据的猜测。

疾病、法律条文、引用、命名实体、具体史实、具体文件结论，不能不加标签直接写。

### 2.2 置信度

- `HIGH`：80% 以上。
- `MED`：50%–80%。
- `LOW`：20%–50%。
- `VERY LOW`：20% 以下。
- `UNKNOWN`：无法判断。

`[FRAME]` 对现实判断、以及 `[GUESS]`，最高只能标 LOW。

### 2.3 不知道时的处理

不知道时，第一句写“我不知道。”不要藏着，也不要编造。

如果只能事后解释结果，不能预测结果，应标为 `[INFERRED]`，并说明这是 post-hoc 解释，不是预测性结论。

如果为了保持前后一致而坚持某个立场，后来发现错误，应公开修正，并说明错在何处。

## 3. 项目定位

项目名称：钢四人物小传 / character biographies。

这是一个为《Hearts of Iron IV》（钢铁雄心4）补充人物小传的轻量级历史沉浸 MOD。

核心功能：在国家领袖、顾问、陆军将领、海军将领等已验证界面中，将鼠标移动到对应人物头像上，即可查看补充人物简介。科学家身份可以保留在机器审计底库中用于解释角色结构，但按当前长期规则默认不写人物小传、不进入常规 Claude 写作名单、不作为补漏优先项；除非用户明确重新开启科学家专项。

项目目标不是新增玩法，而是把原版中只有姓名和头像的人物，还原成有生平、派系、政治立场、军事经历、历史位置和结局的具体历史人物。

当前长期定位为“纯人物小传版”：不主动加入地区介绍事件、决议扩展或额外玩法内容，尽量减少对原版机制和其他 MOD 的干扰。

## 4. 项目整体开发脉络

本 MOD 最初起步于《钢铁雄心4》MOD 制作学习阶段。早期工作主要围绕决议、事件、本地化与人物文件展开，逐步确认 `common/characters`、`localisation/simp_chinese`、`events`、`decisions`、`history/countries`、`interface` 等文件之间的关系。

随后，项目核心逐渐明确为“人物小传”。最初目标是为 PRC 人物补充鼠标悬停简介，使玩家在领袖、顾问、陆军将领、海军将领等界面中，能够通过头像 tooltip 看到人物生平、政治立场、军事经历和历史位置。项目早期参考 Kaiserreich 等大型 MOD 的人物显示思路，但最终收束为更轻量的原版补充型人物小传 MOD。

早期曾探索过地区介绍事件、战争正当化文本、投降/接收事件和“功德林”类接收文本。这些属于历史探索线，不是当前默认主线。当前处理时不得自动把这些旧功能恢复进人物小传主包。

随着覆盖范围扩大，项目进入世界人物小传阶段。覆盖范围从中国相关人物扩展到日本、苏联、德国、英国、美国、意大利、法国以及世界国家领袖、动态领袖、旧式领袖路径。人物范围从国家领袖、顾问、理论家、陆军将领、海军将领，扩展到空军人物和部分国策、事件、决议及 scripted effect 中动态出现的人物。科学家只保留在结构审计底库中，默认不进入写作和补挂流程。

## 6. 人物总表与专题表标准

后续所有补漏、写作、整合、自检，都应以“当前用户明确指定的人物总表或专题复核表”为准。

长期总表原则：

- 只收具名人物，一人一行。
- 科学家可以保留在机器扫描底库中，但默认不进入人工写作主表、Claude 名单和常规入包清单；用户明确开启科学家专项时另行处理。
- 占位符、随机泛名、委员会、临时政府、集体角色、generic 人物不进真人主表。
- 同一个人不因国家领袖、顾问、理论家、将领、国策领袖等多重身份拆成多条；原则上“一人一文”。
- 同人多 key 应放到“Key 明细 / 同人合并参考”里，防止后续写作和整合时漏同步。
- 不能只扫描 `common/characters`。身份与动态路径审计至少同时扫描：`common/characters`、`history/countries`、`common/national_focus`、`events`、`common/decisions`、`common/scripted_effects`、`common/on_actions`、`localisation/simp_chinese`、`localisation/replace/simp_chinese`。
- 重点关注 `history/countries` 中的 `create_country_leader`，这类旧式领袖很容易不在 `common/characters` 中出现。
- 对 `POLITICS_xxx_DESC` 生成的动态领袖，要判断其是否对应具名真人；确认为真人则入主表，集体/占位/疑似虚构角色不入真人主表。

## 7. 人物小传写作原则

用户倾向于“史实、史学评价、可考名言和知名绰号”，而不是普通 AI 简历。

核心原则：

- 一个历史人物原则上只维护一份正文，可被其国家领袖、将领、理论家、顾问、海军将领、情报人员或动态身份复用；科学家身份默认不单独触发写作任务。
- 尽量尊重史实，避免神化、洗白或刻意丑化。
- 资料充分者写经历、派系、立场、历史作用、争议和结局。
- 资料不足者保守简写，不编造。
- 不写空泛套话，例如“著名政治家、军事家，为国家作出重要贡献”。
- 重要人物可写 250–450 字；普通人物 200–300 字；冷门且资料少者提醒用户复核。
- 可考名言、口号、称号、绰号可以自然写入；不可考则不写。
- 带有贬义或争议的称呼要写成“有……之称”“常被称为……”，不要当作绝对事实。
- 直接引语必须严格核查。没有可靠出处，不制造漂亮伪引。
- 人物评价应克制、复杂、可考。

事实核查优先级：

- 中文大陆权威资料、百度百科、党史资料、民国史、抗战史、地方志、人物辞典等可作为基础。
- 不能只看中文来源就武断判错；必要时查英文、日文、俄文、德文等资料。
- 对有中国相关经历的人物，可靠涉华记载应优先写入，尤其是赴华顾问、抗日航空队、东北/满洲、蒙古、新疆、西藏、中苏关系、缅甸战场、援华通道、对日作战、与中国领导人交往等。
- 对敏感人物、争议人物、战犯、独裁者、极端主义者、殖民人物、种族政策相关人物，要写清事实、责任和争议，避免洗白或情绪化丑化。

## 8. Claude 写作任务口径

Claude 只负责写文本，不负责代码、不负责挂载、不负责文件结构、不负责技术判断。

给 Claude 的表应是“一人一行、一人一 key”的写作表，不要把代码字段塞给它。

保留字段建议：

- 序号。
- 人物 key。
- 中文名。
- 所属政权。
- 主要身份。
- 其他身份。
- 优先级。
- 现有文本。
- 是否已有文本。
- 是否重点人物。
- 建议字数。
- 核查重点。
- 可考名言 / 绰号提示。
- 涉华 / 边疆 / 抗战 / 内战线索。
- 敏感点。
- 备注。
- Claude 输出栏。

Claude 输出格式可用于审稿：

```text
四十七、CBIO_ENG_archibald_wavell_desc

§Y阿奇博尔德·韦维尔§!
-----------

正文……
```

注意：上述格式只用于给用户审稿。写入游戏本地化时，不能把 `§Y姓名§!` 和 `-----------` 直接写入 tooltip 正文，否则会导致游戏内重复显示姓名和分隔线、排版混乱。

写入 MOD 时应只写正文。对长文本应根据游戏 tooltip 显示实际情况控制换行；必要时可压成连续段落。

## 9. 显示机制与常见坑点

不要把“有文本”“有 desc”“游戏能显示”混为一谈。

常见显示路径：

1. 显式 `desc = xxx_desc`：多见于 country_leader、corps_commander、field_marshal、navy_leader 等。科学家身份虽然也可能出现 `desc` 字段，但按当前规则只保留在结构审计中，默认不写、不补挂、不列为显示完成项。
2. `idea_token_desc`：顾问、理论家等很多界面通过 `idea_token = xxx` 读取 `xxx_desc`。
3. `POLITICS_xxx_DESC`：旧式或动态领袖常用政治简介 key。
4. `create_country_leader`：可能出现在 `history/countries`、`events`、`national_focus` 中。该方式可直接创建领袖，未必有 `common/characters` 角色块。
5. `add_country_leader_role` / `promote_character`：国策或事件给已有 character 追加或晋升领袖身份，可能需要单独处理动态领袖 desc。
6. 同一人物可能有本体 key、CBIO key、原版小写 key、POLITICS key、idea token key 等多个入口。需要做别名覆盖或同步，避免不同界面显示不同版本。

如果用户说“某人没有小传”，不要直接判定“缺文本”。应依次检查：

1. 人物是否在当前总表或当前专题表。
2. 是否有本地化正文。
3. 角色块是否有 `desc`。
4. 顾问是否走 `idea_token_desc`。
5. 动态领袖是否走 `POLITICS_xxx_DESC`。
6. 是否由 `history/countries`、国策或事件创建。
7. 是否存在同人多 key 未同步。
8. 是否存在本地化 key collision 或被原版短文本覆盖。
9. 最后才判断是否需要补写。

## 10. 历史已修复问题的处理口径

历史上已经修复的问题，不得在新版本自检中反复当成当前风险报告，除非用户上传的新截图、新日志或新包明确证明复发。

可作为历史技术经验保留的类型包括：

- 1939 剧本国家领袖错位问题。
- 动态领袖未继承小传问题。
- 某些国家选择界面提示显示异常。
- `.mod` 文件遗漏。
- 顾问/理论家吃原版 `idea_token_desc`。
- 动态领袖吃 `POLITICS_xxx_DESC`。
- Claude 审稿格式被误写入游戏 tooltip。
- 原版短文本覆盖自定义小传。
- 中文 UI 核心本地化污染。
- 本地化 key collision。
- BOM/编码问题。
- 大括号、desc 位置、脚本 token 格式错误。

历史版本号只能作为“问题曾在哪个阶段出现/修复”的背景，不代表当前版本状态。当前版本状态必须依据当前基准包、当前日志、当前截图和当前试玩反馈判断。

## 12. 打包与文件结构规范

每次打包前至少检查：

- zip 外层是否包含 `.mod` 文件和 MOD 文件夹。
- `.mod` 中 `path="mod/xxx"` 是否匹配实际文件夹名。
- MOD 文件夹内 `descriptor.mod` 是否与外层 `.mod` 关键字段一致。
- 当前目标版本包内 MOD 文件夹名、外层 `.mod` 文件名、内层 `descriptor.mod` 路径应统一为当前版本名，除非用户明确要求沿用旧文件夹名。
- 不要把 Excel、日志、缓存、旧压缩包、测试图片、临时脚本塞进发布包。
- MOD 内不应包含原版核心 UI 本地化整包，尤其不要再引入 `core_l_simp_chinese.yml` 造成 UI 污染。
- 本 MOD 内本地化 key 是否重复。
- 新增/修改 key 是否都存在。
- `common/characters` 中所有 `desc` 引用是否能找到本地化。
- 被用户点名的问题人物是否覆盖所有显示路径：CBIO key、原版 key、idea_token key、POLITICS key、history/focus/event 创建或追加领袖路径。
- 被改动角色文件、国策文件、事件文件、history 文件的大括号是否平衡。
- 日志中重点看：missing localization、duplicate loc key、malformed token、unexpected token、invalid effect/trigger、GUI parse error、history/focus/event 报错。

## 13. 更新日志与工坊说明规则

更新日志分两类：

### 13.1 面向玩家的工坊更新日志

原则：普通玩家不需要看大量技术细节。

应重点写：

- 新增了哪个国家或哪类人物小传。
- 修复了哪些玩家可感知的显示问题。
- 当前仍是纯人物小传版。
- 是否建议重新订阅或清缓存。

不应重点写：

- 过多脚本路径。
- 内部表格字段。
- 大量 key 名。
- 复杂 debug 过程。

### 13.2 自用开发日志

可以写技术细节，包括：

- 读取多少条。
- 写入多少条。
- 跳过多少条以及原因。
- 改了哪些角色文件、国策文件、事件文件、本地化文件。
- 哪些是截图确认、日志确认、试玩确认、人工确认。
- 哪些只是阶段性可接受。

不得在尚未人工审核时写“人工确认完成”。不得在尚未试玩时写“游戏内已完全修复”。

## 14. 后续对话处理建议

## 15. 最低风险原则

处理 MOD 时，应优先选择最小改动方案：

- 能通过新增本地化 key 解决的，不改脚本。
- 能通过补 desc 或别名解决的，不重写角色定义。
- 能只改当前国家文件的，不扩大到全局文件。
- 能不动核心 UI 本地化的，不碰核心 UI 本地化。
- 能保留原版机制的，不引入新机制。
- 对动态领袖，只补显示路径，不改变上台逻辑。
- 对文本整合，只写入正文，不把审稿格式写进游戏 tooltip。

最终目标是：人物简介显示稳定、文本可靠、文件结构干净、对原版机制干扰最小。

## 16. 常驻 source 的维护原则：只写长期规则，不写短期进度

本文件可以持续增强，但增强对象应是长期有效的流程、判断标准、技术经验和风险控制，不是某一轮版本的完成状态。

可以写入本 source 的内容包括：

- 文件优先级规则。
- 新对话串启动流程。
- 人物总表结构与读取方法。
- 原版资料包使用口径。
- 人物显示路径经验。
- Claude 文本清洗流程。
- 整合回写流程。
- 常见错误和历史经验。
- 状态分级标准。

不应写入本 source 的内容包括：

- 当前最新 MOD 版本号。
- 当前最新包名。
- 当前处理到哪个国家。
- 当前批次完成了多少人。
- 某一轮临时待修人物名单。
- 某个对话串里尚未固化的临时判断。

如果需要保存短期状态，应另建“当前交接卡”“当前更新日志”“当前批次表”或“当前人工复核表”。source 永远只作为长期规则，不随每次版本更新而被迫修改。

## 17. 常见来源文件分层与最低配置

新对话串中，来源文件应按功能分层理解，不要混用。

### 17.1 常驻规范文件

示例：

```text
钢四人物小传MOD_项目描述与工作规范_常驻source.md
```

用途：提供长期流程、文本标准、技术经验、风险控制。

限制：不能代表当前版本状态，不能作为当前 MOD 基准包，不能用来判断某个问题“当前已修复”。

示例：

```text
钢四人物小传MOD_全量人物与显示路径总表_*.xlsx
```

用途：查人物、身份、key、路径、现有文本、批次、动态领袖风险、Claude 导出与整合回写。

限制：表格是文件扫描结果和人工管理结果，不等于游戏内试玩确认。表中“有正文 / 有 desc / 已覆盖”必须结合显示路径和试玩反馈判断。

### 17.3 原版参考包

示例：

```text
Hearts of Iron IV.zip
```

用途：查原版 `common/characters`、`history/countries`、`national_focus`、`events`、`decisions`、`ideas`、`scripted_effects`、`on_actions`、本地化和 DLC 路径。

限制：原版参考包不能覆盖当前 MOD 包，不能从原版资料中恢复旧玩法线，也不能代表当前 MOD 文件实际已经修改。

### 17.4 当前 MOD 基准包

示例：

```text
某个当前用户明确指定的 MOD zip
```

用途：整合、打包、查当前包内文件、查 `.mod`、查 `descriptor.mod`、查当前本地化重复 key、查当前角色文件是否真正写入 desc。

限制：只有用户在当前对话串明确说明“这是当前基准包”时，才能作为当前基准。旧包、工坊包、历史包不能自动升格为当前基准。

### 17.5 任务输入文件

包括：Claude 输出、人工复核表、日志、截图、用户手工修改表、对比文本、测试反馈。

用途：执行当前任务。

限制：任务输入不能覆盖当前基准包，除非用户明确要求“把这些内容整合进基准包”。

### 17.6 缺文件时的处理

如果只有 source、全量总表、原版参考包，没有当前 MOD 基准包，可以执行：

- 查人物名单。
- 查身份。
- 查原版路径。
- 查动态领袖候选。
- 导出 Claude 写作名单。
- 做文本清洗复核表。
- 做理论上的整合建议。

但不能可靠执行：

- 实际整合进 MOD。
- 生成可发布新包。
- 判断当前 MOD 文件是否已经写入。
- 检查 `.mod` / `descriptor.mod`。
- 检查当前包本地化重复 key。
- 宣称当前包游戏内已修复。

## 18. 全量总表的推荐结构与读取口径

全量总表应优先采用多工作表结构。不要把一人多身份、多 key、多路径硬塞进一个巨宽表。

推荐工作表及职责：

### 18.1 `人物主表`

回答“这个人是谁”。

原则：一人或一人物 UID 一行。用于查看中文名、英文名/原名、国家标签、身份汇总、是否科学家、是否占位、是否有当前 MOD 正文、计划批次、复核状态等。

注意：人物主表不应承载所有 key 和所有动态入口细节。

### 18.2 `身份明细`

回答“这个人在游戏里是什么身份”。

原则：一身份一行。同一人如果同时是国家领袖、顾问、元帅、将领、海军将领、科学家，应在身份明细中分多行，但使用同一人物 UID。

### 18.3 `显示路径`

回答“这个人通过什么机制出现”。

重点字段包括：入口类型、来源文件、触发方式、character_id、created_leader_name、idea_token、POLITICS_key、显式 desc、推断 desc、是否动态路径。

动态领袖、国策领袖、事件领袖、决议领袖、`scripted_effects` 中追加角色，都必须靠此表追踪。

### 18.4 `Key明细`

回答“哪个 tooltip key 会显示”。

同一人物可能有多个 key，例如：

```text
CBIO_xxx_desc
xxx_desc
idea_token_desc
POLITICS_xxx_DESC
旧式 leader desc
国家别名 desc
```

Key 明细必须记录当前 MOD 是否定义、原版是否定义、是否重复定义、是否短文本、是否需要同步到主 key。

### 18.5 `现有文本库`

回答“当前包和参考资料里到底有什么文本”。

用途：查旧正文、重复 key、空文本、审稿格式残留、异常字符、原版短文本覆盖风险。

### 18.6 `动态领袖待修`

回答“哪些动态上台人物需要专门检查”。

注意：此表中的行不等于都是 bug。它只是动态路径候选和风险集合，需要结合截图、日志、试玩和人工判断。

### 18.7 `Claude写作导出`

给 Claude 或其他写作模型用，只包含写作所需字段，不包含复杂代码路径。

Claude 不负责挂载、打包、脚本机制、desc 路径判断。

### 18.8 `整合回写清单`

用于最后修改 MOD。它应明确写入 key、旧文本、采用正文、是否删除旧定义、是否补角色 desc、是否补 idea_token_desc、是否补 POLITICS_DESC、是否补动态路径、涉及脚本文件。

## 20. 人物显示路径经验总表

不要把“有正文”“有 desc”“能显示”混为一谈。下面是长期经验口径。

### 20.1 国家领袖 / 陆军将领 / 陆军元帅 / 海军将领

常见可行路径：在对应角色身份块中加：

```text
desc = 某个_desc_key
```

再在本地化中定义该 key。

但仍要检查：该身份是否实际被招募、是否被动态追加、是否有另一套旧式 `POLITICS_*_DESC` 路径覆盖。

### 20.2 顾问 / 理论家 / 部长

常见路径有两种：

1. 显式 `desc = xxx_desc`。
2. 通过 `idea_token = xxx` 读取 `xxx_desc`。

很多顾问界面吃的是 `idea_token_desc`。因此同人兼任顾问时，不能只补 `CBIO_xxx_desc`，还要判断是否需要同步或别名到 `idea_token_desc`。

### 20.3 旧式或动态国家领袖

可能走：

```text
POLITICS_xxx_DESC
create_country_leader
add_country_leader_role
promote_character
set_country_leader
```

这类人物不能只看 `common/characters`。必须查 `history/countries`、国策、事件、决议、`scripted_effects`、`on_actions`。

### 20.4 国策 / 事件 / 决议 / scripted_effects 动态角色

动态角色可能不是直接出现在国策或事件里，而是由国策/事件调用 scripted effect，再由 scripted effect 创建或追加角色。

因此查动态领袖时至少搜索：

```text
create_country_leader
add_country_leader_role
add_corps_commander_role
add_navy_leader_role
add_advisor_role
promote_character
recruit_character
retire_character
set_country_leader
idea_token
desc =
POLITICS_
```

### 20.5 科学家

科学家身份仍应被扫描并保留在静态身份底库中，因为它们会影响人物总量、角色文件结构和同人多身份判断。

但当前项目长期规则为：

- 科学家默认不写人物小传。
- 科学家默认不进入 Claude 写作名单。
- 科学家默认不进入常规最终入包清单。
- 科学家身份不计入近期静态缺口和动态缺口优先级。
- 同一人物若兼任国家领袖、顾问、将领或海军将领，应在这些可显示身份中正常处理；不是因为其同时具有科学家身份而排除整个人物。
- v129p—v129s 及此前科学家 GUI 探针已经证明，普通 MOD 新增控件无法取得可复用的当前悬停 Character scope。除非用户明确重新开启独立科研界面专项，不再把“科学家 GUI 攻关”列为默认待办。

机器表中可使用“科学家规则排除”标记。该标记表示“不属于当前写作范围”，不表示文件结构错误。

## 21. Claude 文本处理流程

Claude 或其他写作模型只负责写文本，不负责代码、路径、挂载、打包。

### 21.1 给 Claude 的输入

应提供：

- 人物 key。
- 中文名。
- 英文名/原名。
- 国家/政权。
- 主要身份。
- 其他身份。
- 旧正文。
- 工作类型。
- 建议字数。
- 核查重点。
- 涉华线索。
- 敏感点。

不应提供复杂技术字段让 Claude 判断，例如实际脚本路径、是否要改 GUI、是否要写入哪个文件、是否要删除重复 key。

### 21.2 Claude 输出后的第一步

Claude 写回文本后，第一步不是整合，而是清洗复核。

至少检查：

- 是否漏人。
- 是否多写人。
- 人物 key 是否对应。
- 是否同名混淆。
- 是否错国、错身份、错时代。
- 是否残留 `§Y姓名§!`、`-----------`、`【自检】`。
- 是否有明显伪史、编造名言、过度评价。
- 是否需要人工复核。

### 21.3 写入游戏前必须剥离审稿格式

Claude 审稿格式通常类似：

```text
§Y姓名§!
-----------

正文……

【自检】
……
```

写入游戏本地化时只能保留“正文”本身。不得把 `§Y姓名§!`、分隔线、自检段落写进 tooltip 正文。

### 21.4 人工复核优先

如果表中存在以下列，优先级通常为：

```text
采用正文 > 人工修改正文 > Claude正文 > 旧正文
```

不得用 Claude 自动正文覆盖用户已经人工修改过的文本。

## 22. 整合回写流程

整合进 MOD 前，必须具备：

- 当前 MOD 基准包。
- 已确认采用的正文表。
- 对应人物 key 和显示路径。

整合顺序：

1. 读取当前 MOD 基准包。
2. 提取当前包内已有本地化 key。
3. 对采用正文进行清洗。
4. 删除或替换旧的同名 key 定义。
5. 写入新的本地化正文。
6. 如角色块缺 `desc`，按最小改动原则补充。
7. 如顾问走 `idea_token_desc`，判断是否需要同步 key。
8. 如动态领袖走 `POLITICS_*_DESC` 或 `create_country_leader`，单独处理对应路径。
9. 检查大括号、重复 key、缺本地化、异常字符。
10. 打包前检查 `.mod`、`descriptor.mod`、路径、无关文件。

整合原则：

- 能补本地化，不重写角色定义。
- 能补 desc，不改上台逻辑。
- 能同步别名 key，不改 GUI。
- 能只改当前国家文件，不扩大改动范围。
- 不能用后置本地化文件掩盖旧重复 key；需要明确删除或替换旧定义。
- 不把 Excel、日志、临时脚本、旧包塞进发布包。

## 23. 状态分级的统一写法

任何处理结果都必须标明证据类型。推荐状态如下：

```text
未查
已定位路径
文件确认
脚本扫描确认
文本已清洗
人工文本确认
已写入文件
日志无明显报错
截图确认显示
试玩确认通过
阶段性可接受
复发
待人工确认
规则排除
研究路线终止
不适用
```

禁止把下列状态混写：

- 文件里有文本 ≠ 游戏显示。
- 文件里有 desc ≠ tooltip 读取。
- 脚本扫描无报错 ≠ 试玩通过。
- 没看到问题 ≠ 彻底修复。
- 表格已覆盖 ≠ 当前 MOD 已整合。
- Claude 已写 ≠ 人工确认。

推荐表述：

```text
[文件确认] 当前包中已写入 key，但未试玩。
[脚本扫描确认] 未发现明显重复 key 或括号错误，但未进游戏。
[截图确认] 用户截图显示该人物 tooltip 已出现小传。
[试玩确认] 用户实际进 1936 / 1939 剧本验证通过。
[阶段性可接受] 当前证据下未发现问题，但不等于彻底无风险。
```

## 24. 历史经验附录：后续不要重复踩的坑

以下经验可作为长期参考，但不能替代当前文件、日志、截图和试玩反馈。

### 24.1 不要混回旧功能线

本项目当前长期主线是纯人物小传。除非用户明确要求，不要主动恢复：

- PRC 地区介绍事件。
- 功德林。
- 战争正当化文本。
- 宣战、议和、停止抵抗沉浸文本。
- 接收将领玩法。
- 额外决议扩展。

### 24.2 不要把旧问题当成当前问题

历史上修过的问题只能作为经验，不得在新版本自检里反复列为当前风险，除非新日志、新截图或新包证明复发。

### 24.3 1936 / 1939 才是默认测试口径

默认只按 1936 和 1939 两个剧本处理。不要主动引入 1940、1942 等其他剧本测试口径。

### 24.4 动态领袖必须查路径

动态领袖缺小传时，不要只补一个 `CBIO_xxx_desc`。必须查它是否来自：

- `create_country_leader`
- `add_country_leader_role`
- `promote_character`
- `POLITICS_*_DESC`
- `history/countries`
- `national_focus`
- `events`
- `decisions`
- `scripted_effects`

### 24.5 顾问理论家常吃 idea_token_desc

顾问、理论家、部长界面常常不吃人物主 key，而吃 `idea_token_desc`。同人多身份必须同步，否则会出现领袖界面有小传、顾问界面没有小传。

### 24.6 科学家默认排除

科学家身份保留在机器底库，但默认不写、不交给 Claude、不纳入常规补漏。若人物另有国家领袖、顾问、将领或海军身份，则只处理这些实际可显示身份。不得再把科学家 GUI 路线作为日常开发方向。

### 24.7 Claude 文本不能直入包

Claude 输出要先清洗、复核、剥离审稿格式，再进入人工复核表。不得直接写入 MOD。

### 24.8 中文 UI 核心本地化不要污染

人物小传 MOD 不应携带大段原版核心 UI 本地化文件，尤其不要无必要引入 `core_l_simp_chinese.yml` 一类文件，避免污染界面和兼容性。

### 24.9 `.mod` 和 descriptor.mod 必须检查

发布包必须包含外层 `.mod` 和内层 `descriptor.mod`，并且路径、名称、支持版本等字段应一致。不要只压 MOD 文件夹。

### 24.10 人工修改永远优先

用户人工修改过的表格、正文、采用列，是最高优先级文本来源。不得用自动表或 Claude 输出覆盖。

## 26. 各类任务的标准入口

### 26.1 查人物是否已有小传

先查：人物主表、Key 明细、现有文本库、身份明细、显示路径。

- 哪个 key 有正文。

## 27. 动态显示位专项扫描与保守补丁规则

本节用于固化动态领袖、动态顾问、动态将领、旧式 `POLITICS_*_DESC` 等显示路径的长期处理规则。其核心原则是：**扫描可以全量，修改必须保守；风险可以广泛记录，入包只能白名单化。**

### 27.1 扫描与修改必须分离

动态显示位专项任务不得“扫描到什么就自动写进 MOD”。后续应至少拆成三张表或三个阶段：

```text
全量扫描表：记录所有疑似动态显示路径、风险路径、候选人物和证据。
候选修复表：只保留当前包已有正文、且显示路径疑似漏挂的小传候选。
最终修复清单：只列本轮实际允许写入 MOD 的行。
```

实际回写 MOD 时，只能读取“最终修复清单”或用户明确确认的等效小表。全量扫描表只提供证据，不得直接驱动批量改包。

### 27.2 动态显示位专项的最低扫描范围

涉及动态领袖或动态身份复查时，不能只扫描 `common/characters`。最低扫描范围包括：

```text
common/characters
history/countries
common/national_focus
events
common/scripted_effects
common/on_actions
common/ideas
common/idea_tags
localisation/simp_chinese
localisation/replace/simp_chinese
```

如果原版参考包或当前 MOD 包包含 DLC 同名目录，应同步扫描 DLC 下对应目录。很多国策、事件、scripted effect、顾问和动态领袖路径来自 DLC，根目录扫描不足以判断显示完整性。

### 27.3 重点关键词

动态显示位专项至少搜索以下关键词：

```text
add_country_leader_role
remove_country_leader_role
promote_character
create_country_leader
set_country_leader
add_advisor_role
add_corps_commander_role
add_navy_leader_role
recruit_character
retire_character
idea_token
POLITICS_
desc =
```

如果一个人物在原始身份块已有 `desc`，但通过国策、事件或 scripted effect 移除旧身份后再新增另一个身份，该新增身份必须单独检查是否也挂了 `desc`。不能因为 `common/characters` 中原始身份已有 `desc`，就判定所有动态路径都已显示。

### 27.4 最小补丁原则

动态显示位修复只允许补显示路径，不允许改变玩法逻辑。优先级如下：

1. 能新增或同步本地化 key 的，不改脚本。
2. 能在现有角色块补 `desc` 的，不重写角色定义。
3. 能只改当前国家文件的，不扩大到全局文件。
4. 能只补当前动态身份块的，不整文件替换。
5. 能不引入原版文件的，不复制原版整文件。

如果必须从原版参考包引入某个脚本文件，应先确认当前 MOD 包中没有该文件，且引入目的只限于补显示路径。引入后必须做 diff 白名单审计和编码检查。

### 27.5 禁止“全量改包”

全量扫描任务不得自动批量重写大量 `scripted_effects`、`national_focus`、`events` 或 `history` 文件。尤其禁止把扫描脚本生成的整文件直接入包。

正确做法是：按最终修复清单逐条定位目标块，只写入必要的 `desc = xxx_desc` 或本地化 alias。除非用户明确批准，不得修改任何非显示字段。

## 28. `desc` 写入位置硬规则

本节是脚本层面的硬性规则。违反这些规则通常会导致 `error.log` 中出现 `Unexpected token: desc`、`Invalid effect 'desc'`、`Unknown effect-type`、scripted effect 失效，甚至路线逻辑被破坏。

### 28.1 动态领袖正确写法

`add_country_leader_role` 中的 `desc` 必须写在 `country_leader = { ... }` 子块内部。

正确写法：

```text
角色ID = {
    add_country_leader_role = {
        country_leader = {
            desc = CBIO_xxx_desc
            ideology = some_ideology
            traits = { ... }
            expire = "..."
        }
    }
}
```

错误写法：

```text
角色ID = {
    add_country_leader_role = {
        desc = CBIO_xxx_desc
        country_leader = {
            ideology = some_ideology
        }
    }
}
```

后一种会把 `desc` 放到 effect 顶层，容易被 HOI4 解析为非法 effect。

### 28.2 注释块禁止插入未注释 `desc`

如果原文件中存在如下内容：

```text
#country_leader = {
#    ideology = conservatism
#}
```

不得在其中插入未注释的：

```text
desc = CBIO_xxx_desc
```

因为外层身份块已被 `#` 注释，但新增的 `desc` 没有被注释，游戏会把它当作裸露 token 或非法字段。自动修复脚本必须识别整行注释和注释掉的身份块，不得向注释块注入未注释内容。

### 28.3 顾问、将领、海军、科学家区别处理

- `country_leader`、`corps_commander`、`field_marshal`、`navy_leader` 等身份块可优先补显式 `desc`。
- 顾问、理论家、部长必须先判断是否通过 `idea_token = xxx` 读取 `<idea_token>_desc`。很多情况下同步本地化 key 比改脚本更稳妥。
- `scientist = { desc = xxx_desc }` 只作为结构扫描信息保留。科学家默认不写、不补挂、不列为常规缺口；除非用户明确重开专项，不再继续 GUI 攻关。

### 28.4 禁改字段

动态显示位修复中，除 `desc` 和必要本地化 alias 外，默认禁止修改以下字段或结构：

```text
ideology
traits
expire
visible
available
allowed
cost
ai_will_do
completion_reward
available_if_capitulated
fire_only_once
option
trigger
mean_time_to_happen
set_country_flag / clr_country_flag
add_ideas / remove_ideas
add_timed_idea / add_dynamic_modifier
add_political_power / add_stability / add_war_support
```

也不得新增、删除或重命名 scripted effect、事件、国策、决议、角色 ID、idea token。确需修改玩法逻辑时，必须另立任务，不得混入人物小传显示修复。

## 29. Diff 白名单、编码与 BOM 审计

每次打包前必须生成改动审计。尤其是涉及 `scripted_effects`、`national_focus`、`events`、`history/countries`、`common/characters` 时，不能只检查括号平衡。

### 29.1 Diff 白名单

人物小传显示修复默认只允许以下改动：

```text
新增 desc = xxx_desc
新增或替换本地化 desc key
新增或替换 idea_token_desc alias
新增或替换 POLITICS_xxx_DESC alias
必要时新增 localisation/replace 下的覆盖 key
```

以下改动默认禁止，发现即停止打包并人工复核：

```text
删除或重排原版效果
修改国策奖励、事件选项、决议效果
修改 scripted effect 名称
修改角色 ID
修改 ideology / traits / expire
修改 idea_token
修改 visible / available / allowed / ai_will_do
修改 decision ID 或 tooltip ID
修改触发条件或路线逻辑
批量重编码导致整文件 diff
```

### 29.2 编码与 BOM 规则

HOI4 脚本文件与本地化文件的编码要求应分开处理。

```text
localisation/*.yml：通常保留 UTF-8 BOM。
localisation/replace/*.yml：通常保留 UTF-8 BOM。
非本地化 .txt：不得带 UTF-8 BOM。
```

打包前必须扫描以下目录中的 `.txt` 文件是否带 BOM 或隐藏字符：

```text
common/characters
common/national_focus
common/scripted_effects
common/on_actions
common/ideas
common/idea_tags
history/countries
events
decisions
```

尤其是 `common/scripted_effects/*.txt`。如果 scripted effect 文件开头被 BOM 或隐藏字符污染，游戏可能无法注册该 effect，进而导致国策、事件或决议报 `Invalid effect`、`Unknown effect-type`，甚至路线执行结果错乱。

### 29.3 必查日志关键词

日志自检至少检索：

```text
error.log:
Unexpected token
Invalid effect
Unknown effect-type
Malformed token
Invalid Decision ID
missing localization
duplicate loc key

text.log:
missing localization
duplicate
empty localization

游戏加载相关日志:
Invalid
Unexpected
Unknown effect
malformed
```

`text.log` 为空只能说明本地化层面暂未报错，不代表脚本层面安全。必须同时看 `error.log`、`game.log`、`setup.log`。

### 29.4 静态自检必过项

打包前至少完成：

```text
大括号平衡。
所有 desc 引用都有本地化。
新增 key 无重复或重复有明确 replace 处理。
add_country_leader_role 顶层无 desc。
注释身份块中无未注释 desc。
非本地化 .txt 无 BOM。
diff 仅包含白名单改动。
MOD 包内无 Excel、日志、临时脚本、缓存、旧 zip。
.mod 与 descriptor.mod 路径一致。
```

## 30. 动态路径试玩与稳定版确认规则

动态显示位修复不能只测试“人物 tooltip 是否显示小传”。还必须测试该国策、事件或 scripted effect 的玩法逻辑是否仍按原版预期执行。

### 30.1 动态路径必须双重验证

对每条 P0 动态路径，至少验证：

```text
1. 目标人物是否按原路线正常上台或正常获得身份。
2. 上台或获得身份后，该人物 tooltip 是否显示对应小传。
```

如果目标人物没有按原版逻辑上台，即使某个错误上台人物有小传，也不能判定修复成功。

### 30.2 风险分级测试

建议按下列优先级测试：

```text
P0：本轮实际修改过的 scripted_effect / national_focus / event 动态路径，必须测试。
P1：历史上暴露过问题的同类路径，做回归测试。
P2：新增 idea_token_desc 的顾问、理论家、部长路径，抽测。
P3：只补 common/characters desc 的普通将领、海军、顾问路径，抽测。
```

### 30.3 状态命名

稳定性表述必须分级：

```text
文件确认：文件中已写入，但未进游戏。
脚本扫描确认：静态脚本未发现明显问题，但未试玩。
日志确认：error.log / text.log / game.log / setup.log 未发现相关异常。
试玩确认：用户实际进游戏验证目标路径。
稳定基准：试玩确认 + 日志确认后，才可作为后续任务基准。
```

不得把“脚本扫描确认”写成“游戏内已完全修复”。不得把“text.log 为空”单独写成“无报错”。

## 32. HOI4 / DLC 更新后的版本兼容审计规则

### 32.1 触发条件

出现以下任一情况时，在继续新国家批次、整合文本或打包前，必须先判断是否需要做版本兼容审计：

- 用户明确提到 HOI4、DLC、Paradox、P 社、Steam 近期更新。
- 用户反馈“开 MOD 后某原版国策、事件、决议、路线、UI 布局和不开 MOD 不一致”。
- 用户上传新版原版文件、DLC 文件、更新日志、补丁说明或新版游戏日志。
- 当前 MOD 包覆盖了 `common / events / history / localisation` 中的原版脚本文件。
- 原版更新日志涉及当前 MOD 已覆盖的国家、国策、事件、决议、on_action、scripted_effect、history 文件。

不得在这些情况下直接继续入包，尤其不得直接沿用旧 MOD 里的原版脚本文件。

### 32.2 原版参考包的层级

原版参考包分为两类：

1. 完整原版参考包  
   包含 `common / events / history / localisation / interface / gfx / map` 等完整目录。可用于全面扫描、GUI、头像、地图、脚本、本地化、显示路径等工作。

2. 脚本参考包  
   只包含 `common / events / history / localisation` 等脚本与本地化目录。可用于人物小传脚本显示路径、国策、事件、决议、history、on_action、scripted_effect、本地化等工作；不得用于 interface、gfx、map、头像、GUI、字体、贴图等工作。

如果用户上传的是脚本参考包，必须明确说明“该包对脚本兼容热修够用，但不是完整原版参考包”。不得把脚本参考包误称为完整原版包。

### 32.3 覆盖文件四分类

当游戏或 DLC 更新后，应将当前 MOD 覆盖的原版脚本文件与新版原版参考文件比对，分为四类：

```text
A 类：新版原版已更新，MOD 也覆盖，且包含 CBIO 显示路径补丁。
B 类：新版原版已更新，MOD 也覆盖，但无必要 CBIO 改动。
C 类：新版原版未更新，MOD 覆盖且包含 CBIO 改动。
D 类：新版原版未更新，MOD 覆盖但无必要改动。
```

处理规则：

```text
A 类：以新版原版文件为底，重新注入 CBIO desc。
B 类：优先删除 MOD 覆盖文件，避免回退原版。
C 类：保留。
D 类：考虑删除，减少以后版本冲突面。
```

### 32.4 Rebase 原则

A 类文件不得用旧 MOD 文件手工修一两个字段后继续沿用。正确做法是：

```text
1. 读取新版原版文件；
2. 从旧 MOD 文件中抽取必要的 CBIO desc 注入点；
3. 在新版原版文件中定位对应角色、国策、事件、决议或动态显示路径；
4. 只重新注入人物小传所需 desc；
5. 保留新版原版的国策坐标、前置、效果、AI、事件逻辑、决议条件、history 状态；
6. 静态审计 diff，确认除 CBIO desc 与必要本地化 alias 外无额外改动。
```

禁止事项：

- 不得为了修显示而主动改 P 社玩法逻辑。
- 不得把国策、事件、决议、AI、平衡、坐标修改混入人物小传主包。
- 不得把新版原版修复回退到旧版。
- 不得以“人物小传需要覆盖文件”为理由长期维护整棵国策树。
- 如果确需修原版 UI 布局或玩法，应做可选补丁，而不是并入人物小传主包。

### 32.5 覆盖面瘦身

每次版本兼容热修都应尝试减少覆盖面。

优先删除：

- 当前 MOD 覆盖但没有任何 CBIO desc 或小传显示路径必要改动的文件。
- 旧批次遗留、已无实际用途的原版文件副本。
- 与当前人物小传功能无关的国家脚本、事件、决议、history 文件。

保留条件：

- 文件中确有无法通过独立本地化 alias 解决的显示路径补丁。
- 文件中确有动态领袖、事件动态角色、决议动态角色、国策动态角色所需 desc 注入。
- 删除该文件会导致已验证人物小传显示消失。

### 32.6 版本兼容热修命名建议

版本兼容热修建议命名为：

```text
vXXX_游戏版本_compat_hotfix
```

例如：

```text
v121g_1_19_2_compat_hotfix
```

审计报告必须写清：

- 当前 MOD 基准包。
- 新版原版参考包或脚本参考包。
- 哪些文件被重基准。
- 哪些文件被删除以减少覆盖。
- 哪些 CBIO desc 被重新注入。
- 是否改正文。
- 是否改玩法逻辑。
- 是否手工改 P 社国策、事件、决议、AI、坐标。
- 静态自检结果。
- 游戏内测试建议。

## 33. Debug、控制台与原版运行时报错的判断规则

### 33.1 不要把所有 error.log 都归咎于本 MOD

测试中如果用户通过 debug decision、控制台、强制内战、强制释放、强制完成国策、强制触发事件等方式测试动态领袖或显示路径，`error.log` 可能出现原版脚本运行时提示。

不能只因为报错路径位于 MOD 包内，就立即判定为本 MOD 写错。若该文件是从新版原版 rebase 而来，且报错块没有 CBIO 改动，应先按原版运行时报错处理。

### 33.2 优先判断关键词

优先搜索以下关键词：

```text
CBIO
desc
Unexpected token
localisation
localization
missing localization
duplicate localization
duplicate loc key
idea_token_desc
add_country_leader_role
common/characters
```

若报错包含这些关键词，且指向本 MOD 新增或修改位置，应优先按人物小传 MOD 问题排查。

### 33.3 原版运行时提示的常见类型

以下类型不应自动判定为人物小传 MOD 问题：

```text
create_unit 生成单位位置选择失败
state / province / controller / owner 条件不满足
AI 行为脚本运行失败
原版国策效果运行时报错
原版事件链在 debug 强制触发下状态不足
原版决议被 debug 菜单提前触发
原版 scripted_effect 在非预期局面下运行
原版本体已有的实体、图形、装备、game_rule、recruit_character 噪音
```

处理方式：

```text
1. 确认该报错是否在不开 MOD 或原版脚本中也存在；
2. 确认报错块是否包含 CBIO 注入；
3. 确认是否因 debug / 控制台强制触发造成；
4. 若不是小传注入导致，记录为原版运行时提示或观察项；
5. 不为清理这类提示而修改玩法逻辑，除非用户明确要求做可选补丁。
```

### 33.4 测试结论写法

应使用分级结论：

```text
text.log 为空；
人物小传功能正常；
error.log 无 CBIO / desc / 本地化 / duplicate key / Unexpected token 等本 MOD 相关错误；
若有原版运行时提示，说明其触发条件与来源，不把它写成本 MOD 功能错误。
```

不得把 debug 强制触发的原版运行时提示写成“人物小传 MOD 有 bug”，也不得为了让 `error.log` 绝对为空而随意修改原版玩法。

## 35. 统一 GUI Tooltip 路线的最终结论

### 35.1 v129p—v129s 的研究结论

统一Tooltip实验已经确认：

- 直接向原生政治领袖头像或将领行添加 `context_aware_tooltip`，不会产生可用人物探针。
- 删除角色身份原生 `desc` 后，小传会消失，但自定义Tooltip仍不会出现，说明不是被原生desc遮挡。
- 政治界面可以加载新增可见子控件，但新增普通按钮不自动继承父头像的Character scope。
- 对新增按钮使用 scoped tooltip 时，日志明确提示该GUI类型不支持。
- 将领候选行中的新增子控件没有按预期实例化。
- 此前科学家界面的同类探针同样未取得可用人物scope。

正确技术解释：

> `context_aware_tooltip` 依赖HOI4引擎预先注册的控件、窗口控制器和数据提供器。  
> GUI文件只能声明Tooltip，不能让任意新增控件自动获得“当前悬停人物”Character token。

### 35.2 后续禁止事项

除非用户明确要求重新做独立研究，不得：

- 再次尝试把任意普通 `buttonType` 当成通用人物scope入口；
- 再次删除正式人物身份 `desc` 做同类探针；
- 把v129p、v129q、v129r、v129s中的interface文件带入正式包；
- 把冈田启介、寺内寿一的无desc测试状态带入正式包；
- 将统一GUI路线写成“仍待攻克的最后一步”；
- 为追求统一Tooltip而扩大核心GUI覆盖面。

项目主线已经明确：

```text
静态身份 → 身份块desc
动态新增身份 → 实际add_*_role路径
运行时新建人物 → create_*路径的完整版例外
顾问 → 显式desc或idea_token_desc
旧式动态领袖 → POLITICS_*_DESC或实际创建块
```

## 39. v130a 已发现的版本差异与减负方向

本节记录v130a时点已经确认的维护差异，以及v130b只读语义复核形成的修正结论。新版本修复后应在后续交接卡中标记为历史已修复，不得永久当作当前问题。

### 39.1 完整版未同步的52处idea_token清理

精简版v129o已经在以下6个角色文件中清理52处非必要 `CBIO_UNLOC_* idea_token`：

```text
common/characters/PAN.txt

```

完整版v129n仍保留旧token，并比精简版多52个对应本地化键。

v130b只读复核确认：

- 六个文件在v129o与v129n之间合计只有52行差异；
- 差异全部且仅为 `CBIO_UNLOC_*` 与原版 `idea_token` 的替换；

- 没有发现 `desc`、姓名、头像、traits、顾问槽位或其他脚本差异；

```text
localisation/simp_chinese/zz_v129c_initial_leaders_namefix_l_simp_chinese.yml
```

- 该文件只有这52个键，没有其他内容需要保留。

结论：

- 不是当前已确认游戏内错误；
- v129n已经通过初步试玩；
- 但精简版和完整版的静态角色文件不再完全同步；
- 后续完整版重建时应从v129o同步这6个角色文件；
- 同步后再次确认包内不存在 `CBIO_UNLOC_*` 引用；
- 确认后可删除整个上述本地化文件；
- 必须先做独立测试包，不直接覆盖v129n稳定基准。

## 40. 自动重建、版本更新与发布闸门

### 40.1 自动重建目标

长期应将角色文件和动态脚本覆盖从“手工改一次”升级为可重复重建。


输出：

```text
本地化文件

原版SHA-256
desc新增数量
desc具体值变更
desc外差异
缺失正文

发布白名单
```

### 40.2 角色文件重建标准

对仅为人物小传覆盖的角色文件，理想标准是：

> 删除MOD新增或替换的 `desc`、明确批准的姓名显示修正和已批准的idea_token清理后，应能解释与当前原版的全部差异。

不得因为一个角色文件曾经稳定，就永久沿用旧原版全文。

### 40.3 动态脚本重建与语义白名单标准

涉及事件、国策、决议、scripted effect、on_action或国家历史文件时：

- 必须以当前原版全文为底；
- 从旧MOD抽取必要 `desc` 注入点；
- 在新原版中重新定位；
- 只注入白名单字段；
- 不复制旧版玩法逻辑；
- 不使用后置文本掩盖脚本结构差异；
- 必须比较每个 `desc` 的具体旧值与新值；
- 必须检查新 `desc` key 是否有有效本地化正文；
- 必须判断删除覆盖文件后人物小传是否回退；
- 不得仅凭“desc净增为0”或“剔除desc后相同”判定文件冗余。

判断规则：

```text
desc = "" → desc = CBIO_*_desc
原版desc键 → CBIO_*_desc
```

均属于有效人物小传覆盖。只要对应正文有效，且删除后会回退，就必须进入保留白名单。

### 40.4 发布前最低闸门

每次新包至少通过：

```text

7. 本地化BOM、语言头、重复键、缺失desc检查；
8. 非本地化txt无BOM；
9. 文件哈希与原版对照；
10. .mod、descriptor和内部目录一致；
11. 1936与1939测试；
12. P0动态路径双重验证；
13. error.log、text.log、game.log、setup.log检查；
```
