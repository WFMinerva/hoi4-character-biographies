# AI协作项目管理手册（可迁移）

> 本文件与具体项目无关，是从《钢四人物小传》维护实践中提炼的方法论。开新项目时整体复制带走，或只复制第1节的引导词。项目内规则仍以根目录`AGENTS.md`为准。

## 1. 新项目引导词（直接粘贴给AI）

```text
这是一个长期维护项目，你来接手。先读根目录AGENTS.md——它是总入口，含状态快照（注意核对日期是否过期）、当前待办、目录地图（每个目录能不能动）、强制规则和推荐阅读顺序；再读docs/CURRENT_BASELINE.md（版本状态唯一裁决点）和docs/HUMAN_DECISIONS.md（人工裁定台账）。

工作规则：先只读扫描并列出确认事实/推测/涉及文件/最小方案，未经我批准不写源码；机器扫描结果只是候选，不是确认BUG，缺口不等于缺陷；AI生成的内容未经我审定不得进入发布物；每次改动后运行审计脚本（见AGENTS.md），全绿才算完；不得自封"稳定版"，只有我实机确认后才能更新基准；git提交、推送、发布、上传等动作逐项向我确认；禁止顺手修复任务外问题、禁止批量格式化、禁止破坏性git命令。任务收尾时，把新产生的经验和我口头说过的规矩回填到对应手册——这是强制步骤。
```

## 2. 十条核心原则（按价值排序）

1. **单一总入口**：根目录`AGENTS.md`是唯一入口，包含五项：状态快照（带日期+过期提醒）、待办（按优先级）、目录地图（每个条目标注"能不能动"）、通用规则、推荐阅读顺序。任何AI打开仓库都知道先读它。
2. **版本状态唯一裁决点**：一份`CURRENT_BASELINE.md`说了算。旧文档、旧包、旧报告里的状态描述一律不得反向覆盖它；历史内容标日期归档，不与活跃文档混放。
3. **人工裁定台账**：人读的`HUMAN_DECISIONS.md` + 机读的`decisions.json`双写。AI正文未经人工批准不进发布物。用户口头裁定最容易丢——听到"记住""以后都"这类话，当场落台账。
4. **机器扫描=候选，不是结论**：机器底账只用于找候选；任何"疑似问题"必须经语义裁定才能写成BUG。警惕机器口径的系统性缺陷（本项目6421条底账漏算一条显示路径，导致124人全部误报）。
5. **审计即闸门**：提交前必跑审计脚本；脚本默认只读、失败非零退出；日常审计检查"当前差异是否合法"，而不是"是否永远等于旧基线"——这两者必须分开，否则合法修改永远跑不过。
6. **文档分层**：活跃文档与历史文档物理分开（`docs/`与`docs/archive/`）；每份活跃文档开头一行指回总入口；归档原文不动，写一份archive README说明每份是什么时点的什么记录。
7. **最小改动**：任务范围外不动；不顺手修复；不批量格式化/重排/改编码；默认允许改什么、默认禁止改什么，写成明文清单。
8. **状态分级表述**：AI只能说"文件确认/静态检查通过/测试包已生成"；只有用户实机确认后才允许说"稳定"、才允许更新基准和打tag。
9. **高风险动作逐项确认**：git mutation、推送、发布、上传、删除，每次单独确认；一次授权不形成惯例。
10. **经验闭环**：每次大任务收尾强制回填——这次踩的坑进故障手册、用户口头规矩进裁定台账、方法论进本手册。会话导出（wire.jsonl等）定期挖掘，很多关键经验只存在于对话里。

## 3. 仓库骨架模板

```text
AGENTS.md                 # 总入口（快照/待办/目录地图/规则/阅读顺序）
README.md                 # 对外门面
CHANGELOG.md
docs/
  CURRENT_BASELINE.md     # 版本状态唯一裁决点
  HUMAN_DECISIONS.md      # 人工裁定台账（人读）
  WORKFLOW.md             # 日常流程
  *_PLAYBOOK.md           # 分领域经验手册
  KNOWN_RISKS.md          # 高风险边界速查
  INCIDENTS.md            # 故障/原因/防复发
  RELEASE_CHECKLIST.md    # 发布闸门
  archive/                # 历史文档（标日期，原文不动，附README索引）
workbench/                # 人工工作台：pending/ approved/ decisions.json/ 底账
tools/                    # 审计与构建脚本（默认只读，自动修复须显式--apply）
audit/
  baselines/              # 基线manifest（机器生成，勿手改）
  allowlists/             # 例外登记（逐任务、有理由、有范围）
  data/                   # 机器扫描底库（只读参考）
src/                      # 源码（共同来源单一维护，禁止两棵重复树）
build/ releases/          # 构建暂存与产物（工具写入）
reference/                # 本机路径配置（gitignore，附example）
```

```markdown
- 当前版本/基线、确认状态、测试口径。

## 0.2 当前待办（按优先级）
1. ...

## 0.3 目录地图
| 路径 | 用途 | 能不能动 |

## 0.4 推荐阅读顺序
1. 本文件 2. CURRENT_BASELINE 3. HUMAN_DECISIONS ...

## 通用规则
- 每次任务开始必须执行：（只读扫描、git status、最小方案）
- 来源优先级：用户指令 > 人工裁定 > 基准卡 > 源码 > 机器底库
- 默认允许的修改：……
- 默认禁止的修改：……
- 审计入口：……
- 状态与发布：AI不得自封稳定；只有用户确认后……
```

## 5. 新项目落地步骤

1. 建仓库骨架，先写`AGENTS.md`（用第4节骨架）和`CURRENT_BASELINE.md`——哪怕内容很少。
2. 第一次"导入基线"时做等价验证（哈希级），把基线manifest固化到`audit/baselines/`，此后日常审计只查差异合法性。
3. 审计脚本随项目生长：每踩一个可机器化的坑，就把它变成一条check，而不是只写进文档。
4. 每次任务收尾执行"回填三问"：用户这次说过什么口头规矩？踩了什么新坑？哪份手册该更新？
5. 阶段性（或换AI前）做一次会话导出挖掘，把只存在于对话里的经验落进文档。

## 6. 本手册自身的维护

发现新的通用方法论时追加到对应章节；项目特定内容不要写进来（那属于各项目的AGENTS.md和手册）。本手册的最新副本存放在《钢四人物小传》仓库`docs/scaffold/PROJECT_MANAGEMENT_PLAYBOOK.md`。
