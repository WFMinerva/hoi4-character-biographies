## 一、审计目的

此前项目主要以“人物是否已经写过小传”为统计口径。随着覆盖范围扩大，这一口径已经不足以判断游戏内是否真正显示人物小传。

HOI4 的人物简介实际属于身份级数据。同一人物可以同时或先后具有：

- 国家领袖；
- 政治顾问；
- 陆军将领；
- 陆军元帅；
- 海军将领；
- 科学家；
- 国策、事件、决议或脚本效果动态增加的身份；
- 运行时通过 `create_country_leader` 等命令新建的身份。

因此，本轮审计将基本统计单位改为：

> **人物 × 身份 × direct/instance路径 × 动态生成路径**

本轮的目标不是立刻修复全部筛查项，而是建立一套可以持续复用的工程化底账，回答以下问题：

1. 原版到底存在多少人物和身份实例；
2. v129o、v129n已经覆盖了哪些静态身份；
3. 哪些人物身份仍无 `desc`；
4. 哪些身份通过事件、国策、决议等路径动态生成；
5. 完整版覆盖文件是否只修改了小传文本；
6. 本地化是否存在缺失、重复、编码或版本不同步问题；
7. 哪些文件可以减少覆盖，从而提高兼容性。

## 二、此前统一 GUI Tooltip 路线的结论

在 v129p—v129s 中，项目对“通过统一 GUI Tooltip 获取当前悬停人物 token”的方案进行了多轮实验。

测试结果包括：

- 直接给政治领袖和将领控件添加 `context_aware_tooltip`：不显示；
- 删除原生身份 `desc` 后重试：原生小传消失，但探针仍不显示；
- 政治界面可以加载新增独立子控件；
- 新增普通按钮使用 `context_aware_tooltip` 时，日志明确提示该 GUI 类型不支持 scoped tooltip；
- 将领候选行没有实例化新增子控件；
- 此前科学家界面的同类尝试同样没有取得可用人物作用域。

技术结论：

> HOI4 v1.19.2 没有向普通 MOD 开放一个可供任意 GUI 控件调用的“当前悬停人物 Character token”。  
> `context_aware_tooltip` 依赖引擎预先注册的控件及数据提供器，新增控件不会自动继承头像或人物行的 Character scope。

因此，统一 GUI Tooltip 不能替代身份 `desc`。项目主线应继续采用：

- 静态身份：在 `common/characters` 对应身份块挂载 `desc`；
- 动态新增身份：在实际 `add_*_role` 等路径精确补挂；
- 运行时新建人物：在 `create_*` 路径做完整版例外覆盖；
- 不再重复尝试通用悬停人物 token 方案。

v129p—v129s均为研究实验版，不得作为正式基准或入包来源。

### 2. 如何理解1115条“身份存在但无desc”

这1115条不能直接视为1115个BUG，可能包括：

- C类非领袖；
- 虚构、占位或不可核实人物；
- 同一人物的备用身份；
- 不会在实际界面显示的身份；
- 只用于特定DLC、路线或条件的实例；
- 已有其他身份小传，但当前身份仍需判断是否应复用；
- 尚未进入人工写作和裁定批次的人物。

后续必须按项目规则分类：

1. 重要领袖优先；
2. C类领袖进入人工审核；
3. C类非领袖原则上不写；
4. 科学家默认不写；
5. 真人多身份应核验每个实际显示身份；
6. 不能因为人物已有正文，就默认所有身份均已覆盖。

### 3. 如何理解1113条“身份未覆盖”

这部分表示对应原版角色文件或该身份实例尚未进入v129o/v129n。

它们属于：

> **覆盖范围外待办**

不是当前稳定版中已经完成内容的回归BUG。应继续按国家批次、可释放国家、动态政权和特殊身份逐步推进。

### 4. 科学家口径

原版共识别103个科学家身份，其中60条在当前角色文件中存在有效 `desc`。

但项目当前规则是：

> 科学家默认不写人物小传。

因此科学家数据只保留作结构底账，不作为近期补漏任务。未来若项目规则改变，应重新分类，而不是直接使用当前覆盖率判断完成度。

### 3. 2700条疑似缺口不等于2700个确认BUG

动态路径中的机器筛查会将以下情况列为候选：

- 人物静态同类身份没有有效 `desc`；
- 动态新增身份块本身没有 `desc`；
- 完整版已经覆盖该文件，但相应创建块仍没有有效 `desc`；
- 人物scope无法可靠解析；
- 运行时新建人物没有稳定character token；
- 对应国家或人物尚未进入当前覆盖范围。

其中可能包含：

- 同一个人物在多条事件、国策和分支中重复出现；
- 多个意识形态选项；
- 备用路线或不会实际触发的路径；
- C类人物或占位人物；
- 原版已经通过其他身份继承机制正确显示；
- 只需要保留路径索引、不需要补小传的退休和移除命令。

因此必须先去重、分类和实测，不能批量向2700条路径直接注入 `desc`。

### 4. 优先级解释

#### 高优先级

主要指：

- v129n已经覆盖来源文件；
- 但 `create_country_leader` 或动态身份块仍没有有效 `desc`；
- 静态同类身份也无法提供有效小传基础。

这类应优先核验，因为它们最接近“完整版理论上准备补齐，但实际路径仍可能漏传”的情况。

#### 中优先级

主要包括：

- 覆盖范围外动态路径；
- 人物scope未解析；
- 静态身份无 `desc` 基础；
- 同一人物多身份疑似漏挂；
- 尚未人工判断真人、C类、领袖或是否实际显示。

中优先级数量很大，不适合一次性处理，应按国家和命令类型拆批。

### 5. 运行时新建人物

共识别224条运行时新建路径，包括：

- `create_country_leader`
- `create_corps_commander`
- `create_field_marshal`
- `create_navy_leader`
- `generate_scientist_character`

这类路径通常不能由精简版的 `common/characters` 解决。

处理原则：

- 精简版：登记为结构性例外，不为补齐它们而覆盖事件、国策和决议；
- 完整版：按当前原版文件重建，在实际创建块中精确补入 `desc`；
- 科学家创建路径按当前规则排除；
- 没有稳定token的人物必须使用运行时名称和来源路径单独管理。

> v129n的事件文件已经完成1.19.2重建，但其静态角色文件尚未完全同步v129o最后一轮 `idea_token` 清理。

这不是当前已确认的游戏内错误，v129n也已经通过初步试玩。但两条稳定版本线的静态内容不再完全一致，会增加后续维护成本。

建议：

- 以v129o的6个已清理角色文件为来源；
- 单独制作完整版同步测试包；
- 不直接覆盖当前v129n稳定基准；

## 九、扫描口径差异与限制

### 1. 原版角色文件和人物数量的解析口径差异

v130a-1宽口径汇总记录：

- 原版角色文件：232个；
- 原版人物：5404个。

v130a-2严格静态身份解析器记录：

- 可解析角色文件：231个；
- 可解析人物：5283个；
- 身份实例：6421条。

两套解析器的身份实例总数完全一致，均为6421条。

差异来自：

- 宽口径统计会计入文件级或人物容器级记录；
- 严格解析器只统计成功进入标准 `characters = {}` 结构并可形成身份实例的人物；
- 个别文件或人物没有形成目标身份块，因此不会进入严格人物计数。

因此：

- 项目对外总览可继续使用v130a-1的232个文件、5404个人物；
- 身份审计应以6421条身份实例为核心；
- 不应将121个人物计数差异理解为MOD漏读或文件丢失。

### 2. 人物scope推断不是百分之百可靠

动态表优先按以下顺序推断人物：

1. 命令直接值；
2. `character =` 字段；
3. 外层人物scope；
4. 运行时 `name =`；
5. 无法解析。

低置信度记录可能只是本地化名称、脚本变量或动态对象，不一定是稳定character token。

### 3. 国家Tag可能是DLC或来源前缀

动态表中的Tag优先来自：

- 人物key前缀；
- 外层国家scope；
- `history/countries`文件名；
- 来源文件前缀。

因此BFTB、LAR等值可能是DLC/文件前缀，而不是国家Tag。所有重点项仍应结合来源文件、事件ID、祖先路径和人物名称判断。

### 4. 机器筛查不能代替项目裁定

机器无法可靠判断：

- 人物是否真实存在；
- 是否为C类；
- C类人物是否为领袖；
- 是否应按名字来源说明入包；
- 是否属于项目当前写作范围；
- 路线是否实际可触发；
- 玩家是否能在目标界面看到该身份。

因此本轮审计的作用是建立底账和缩小人工范围，不是自动形成最终入包清单。

## 十三、最终结论

v130a完成并经过v130b只读语义复核后，项目的技术性质可以明确界定：

> 《钢四人物小传》不是一个依赖单一Tooltip技巧的界面MOD，而是一套人物身份数据、动态生成路径、本地化文本和原版版本差异的持续维护工程。

本轮最重要的成果不是发现了多少“错误”，而是建立了四层可追溯底账：

1. **人物静态身份层**：6421条身份实例；
2. **动态生成路径层**：7906条有效人物脚本路径；
3. **本地化引用层**：7314个简中键及4980处完整版新增 `desc` 引用；
4. **文件覆盖与版本差异层**：包级、文件级哈希、原版重建一致性和脚本语义复核。

当前稳定版没有发现本地化硬错误或玩法逻辑污染。真正需要处理的是：

- 完整版与精简版的52处静态清理不同步；
- 同步完成后清理52个孤立 `CBIO_UNLOC_*` 本地化键；
- 257条高优先级动态候选的人工复核；
- 1115条静态无 `desc` 身份的规则分类；
- 1113条覆盖范围外身份的持续批次推进。

同时，七个国家历史文件的复核形成了一项长期工程规则：

> 机器审计不能只统计 `desc` 行数，也不能把“剔除desc后与原版相同”直接解释为文件冗余。  
> 必须比较 `desc` 的具体值、确认本地化正文，并判断删除后是否造成实际人物小传回退。

因此：

- EGY、ISR、JOR、LEB、LIB、PAL、SYR七个国家历史文件属于必要运行时覆盖；
- 它们合计保护18个运行时领袖小传；
- 正式冗余脚本覆盖候选为0；
- 旧“七文件可删除”结论必须归档，不得继续执行。

后续不应再追求一个不存在的“万能GUI入口”，而应继续把身份 `desc`、动态路径例外、原版重建和语义白名单流程自动化、可追踪化和可审计化。
